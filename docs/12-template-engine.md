# 12 — Template Engine

## Locked implementation

Templates use a custom versioned JSON format. Zod is the canonical validator, and a custom data binder resolves an explicit allowlist of certificate fields. PDFKit consumes the validated/bound representation; qrcode produces QR image data for the QR element.

## Requirements

Templates must support:
- text
- images
- dynamic fields
- QR
- signatures
- alignment
- font
- color
- position
- size
- page dimensions

## Format version 1 contract

For newly created templates, `px` is a logical design coordinate at 96 units per physical inch. Page presets are defined once in `packages/template-engine`: A4 (210 x 297 mm), A5 (148 x 210 mm), B5 ISO (176 x 250 mm), and B5 JIS (182 x 257 mm), with portrait/landscape orientation. Raster image pixel dimensions remain resolution metadata and never become PDF physical dimensions. Existing definitions stay unchanged; their immutable renderer revision determines whether coordinates use the historical direct-point behavior or the logical-coordinate conversion.

The normalized root contains `format_version: 1`, a pixel page from 100 through 5000 pixels per dimension, and at most 200 ordered elements. Element order is the stable z-order. Coordinates and dimensions are finite, non-negative, bounded to the page, and cannot use `NaN` or infinity. Objects are strict: undocumented keys are rejected.

Supported elements are `text`, `image`, `signature`, `qr` and `shape` (`line` or `rectangle`). Colors are six-digit hexadecimal values; opacity is from zero through one. Bundled text families are `Noto Sans Thai` and `Noto Serif Thai`, with weight 400 or 700. An unbundled font requires an explicit validated font `asset_id`. A text element has exactly one literal value or allowlisted binding. Image/signature references accept only validated raster assets, and font references accept only validated font assets; purpose/MIME matching is rechecked atomically during publish.

Format version 1 bindings are exactly:

- `recipient.display_name`
- `project.name`
- `training.name`
- `training.code`
- `certificate.number`
- `certificate.issued_at`
- `verification_url`

Unknown paths, nested traversal, prototype fields and expression syntax are rejected. Preview uses fixed synthetic values and does not accept or persist recipient data.

## Asset validation profile

The authenticated admin image-preview route serves only `ACTIVE` PNG/JPEG assets that belong to the requested organization and template. It reads bounded bytes through the storage abstraction, verifies stored size and SHA-256 identity, returns the canonical MIME type with `Cache-Control: private, no-store`, and never exposes or redirects to an object-storage key. Font, quarantined, rejected, archived, foreign-template, and foreign-tenant assets are not served by this route.

Phase 4 accepts PNG, JPEG, TrueType and OpenType assets only. SVG, HTML, scripts, archives and remote/local paths are prohibited. The API enforces the configured upload limit (5 MiB by default and no more than 10 MiB), matches declared MIME to content signature, bounds raster dimensions to 4096 pixels and 16 million pixels, rejects multi-page images, and validates bounded font table directories and required tables. Filenames are normalized for display only; private object keys are generated by the server.

## Security

The template definition is data, not executable code.

Do not allow arbitrary JavaScript execution.

The data binder must not use `eval`, `Function`, dynamic module loading or unrestricted property traversal. Binding names are matched against a versioned allowlist and resolved from a purpose-built rendering context containing minimum required fields.

Remote resource loading should be disabled or allowlisted during PDF rendering.

Template assets must be uploaded to private storage, validated and marked `ACTIVE` before they can be used for publishing. Definitions reference validated asset records; they must not contain arbitrary local paths, bucket paths or remote URLs.

## Versioning

Template versions follow `DRAFT → PUBLISHED → ARCHIVED`.

Every published template definition and its asset links are immutable. The PostgreSQL reference schema enforces this with status constraints and triggers. An archived published version remains immutable and its assets must remain available for historical rendering.

To change it:
- create new version
- preview
- publish
- new certificates reference new version

Existing certificates remain tied to their original version.

Any existing `DRAFT`, `PUBLISHED` or `ARCHIVED` version may seed a new draft under the same active template. This is a copy-forward operation, not a rollback: the historical source version and its lifecycle timestamps remain unchanged, while the new version always starts as `DRAFT` with no publication timestamp. Every referenced asset is revalidated as active, type-compatible and owned by that same template before the new draft is created; missing or ineligible assets fail the operation without silently changing the definition.

Publishing must be atomic: validate the definition, bindings, asset ownership and asset status, then set `PUBLISHED` and `published_at` in one transaction. A generation job accepts only a published version from the same organization.

## Renderer handoff contract

The template engine does not load infrastructure resources. The trusted worker loads the immutable published template and validated private asset bytes, maps the issuance snapshot into the allowlisted binding context, obtains the final verification URL from the trusted token/application boundary, and then calls `packages/certificate-renderer`.

The renderer boundary accepts only:

- format-version-validated template data
- issuance-snapshot binding values plus immutable certificate number/date
- the server-selected renderer revision
- the final verification URL string
- exactly the template-referenced validated asset bytes with purpose, canonical MIME and SHA-256 identity

Storage keys, database objects, Redis/queue objects, signing keys, raw token services, local paths and remote fetch instructions are not renderer inputs.

## Deterministic rendering contract

- Validate and normalize page dimensions, positions, colors, font references and element ordering before rendering.
- Use approved bundled/private fonts and validated private assets only.
- Define stable z-order and text-layout behavior per template format version.
- The same template version, asset hashes, binding data and renderer revision must produce the same approved output behavior.
- Changing schema, binder or layout semantics requires a new supported template-format/renderer revision and must not mutate historical versions.

## Admin design previews

The Template Builder and Template Library use the same browser-side read-only visual surface to interpret canonical element order, coordinates, opacity, text alignment, image fit, signature contain behavior, shapes and QR placement. These previews are design aids rather than certificate render output.

- Image and signature elements are created only after the user explicitly selects an `ACTIVE` PNG/JPEG asset. The editor never chooses the first, latest or imported-background asset implicitly.
- Inline picker uploads use the canonical private asset upload lifecycle. A non-`ACTIVE` result is communicated and is not inserted into the definition.
- Imported full-page image elements are presented as locked backgrounds by default, while remaining canonical `image` elements in the saved definition.
- Design and library QR graphics encode only `https://example.invalid/verify/sample`. Production QR remains generated by the isolated certificate renderer from the trusted final `verification_url` supplied for issuance.
- Library collection responses select one bounded preview summary per template: highest `PUBLISHED` version, otherwise highest `DRAFT`, otherwise the highest remaining version. Private image content remains tenant-authorized and is loaded lazily near the viewport.
